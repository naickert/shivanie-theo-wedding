# Shivanie & Theo Wedding Website — Technical & Functional Spec

**Status:** v1 (prototype → production)
**Owner:** Theo Naicker
**Last updated:** May 2026

---

## 1. Overview

This is the official wedding website for Theo Naicker & Shivanie's three-day Tamil wedding (17–19 December 2026, Durban + KZN North Coast). It serves three audiences:

1. **Guests** — view event details, RSVP, read cultural context, get travel info.
2. **The couple** — track RSVPs, export attendance by event, manage guest list.
3. **Search engines** — explicitly *not* indexed (private wedding, `noindex, nofollow`).

### Why custom, not Withjoy / Zola / The Knot?

- **Cultural fit.** Off-the-shelf platforms assume a one-day Western wedding. A three-day Tamil wedding needs per-event invitations (not every guest is invited to every event), per-event dress codes, and a cultural-guide page for non-Tamil guests.
- **Privacy.** Bride's home address must be gated behind an invite code, not public.
- **Cost.** Withjoy is "free" but monetises via vendor referrals and reception data. Custom + Cloudflare Pages = ~R200/year, no third-party data sale.
- **Ownership.** All RSVP data lives in *our* Google Sheet. Export, delete, migrate at will.
- **Bilingual.** Tamil typography and bilingual labels need real CSS + `lang="ta"`, not a localisation plugin.

## 2. Scope

### In scope (v1)

- Hash-routed SPA: home, story, celebration overview, three event detail pages, cultural guide, travel, FAQ, registry, RSVP, thanks, not-invited.
- Personalised invite-link system (`?i=CODE`) that hydrates a party object and gates content per-event.
- RSVP form with: per-event attendance, per-guest dietary requirements, message to couple, song requests.
- Local-first persistence with optional Google Apps Script backend (Google Sheet as the system of record).
- Admin dashboard at `/admin/` — passphrase-gated; totals, parties × events grid, CSV export.
- Bilingual Tamil/English chrome (titles, key cultural terms).
- Mobile-first, WCAG AA, prefers-reduced-motion honoured.
- Print stylesheet (for the couple to print attendance lists).

### Out of scope (v1)

- Email invitations (WhatsApp + website only — see `email-templates/README.md`).
- PDF invitation downloads.
- Native apps.
- Multi-language toggle beyond bilingual chrome (no full Tamil translation).
- Live chat / guest messaging.
- Photo upload during the event (handled via shared Google Photos album, linked from thank-you message).
- Payment / contribution flows.
- Search.
- Server-side rendering.
- Analytics beyond Cloudflare's built-in pageviews.

## 3. Tech stack

| Layer | Choice | Rationale |
|---|---|---|
| Markup | Static `index.html` (single page) | No build step. SPA shell only. |
| Styles | Hand-authored CSS, custom-properties design system | Tokens in `css/tokens.css`. No Tailwind/Sass. |
| Scripts | Vanilla ES modules (`<script type="module">`) | No bundler. Modern browsers only. |
| Routing | Custom hash router (`js/router.js`) | Works on static hosting, no server config. |
| State | Custom pub/sub store (`js/state.js`) | <40 lines, no React/Vue. |
| Data | Static JSON files + a `guests.json` generated by the couple | `data/events.json`, `data/venues.json`, `data/guests.json`. |
| Persistence (prototype) | `localStorage` | Couple can run the prototype with zero backend. |
| Persistence (production) | Google Apps Script `doPost` → Google Sheet | Free, owner-controlled, CSV-friendly. See `PRODUCTION.md`. |
| Hosting | Cloudflare Pages, custom domain `shivanieandtheo.co.za` | Free tier, fast SA edge. |
| Fonts | Google Fonts (dev) → self-hosted subsets (prod) | Reduces above-fold KB & external DNS. |

**No build step.** `index.html` references CSS and ES modules directly. Deploy = push to `main`.

## 6. Data model

### 6.1 `data/events.json`

Three events, each with bilingual labels, datetime, venue reference, dress code, capacity, and tone notes. See file for full schema; key fields:

```
{
  "id":         "mehendi" | "nalangu" | "ceremony",
  "label_en":   string,
  "label_ta":   string (Tamil script),
  "date":       "YYYY-MM-DD",
  "day":        "Thursday" | "Friday" | "Saturday",
  "start":      "HH:MM" (24h SAST),
  "end":        "HH:MM",
  "venue_id":   string  (FK → venues.json),
  "dress_code": string,
  "capacity":   integer,
  "open_bar":   boolean,
  "vegetarian": boolean,
  "tone":       short prose describing the vibe
}
```

### 6.2 `data/venues.json`

Map keyed by venue id. Includes `address_display`, `city`, `maps` (Google Maps URL), `parking`, `accessibility`. The bride's home has `private: true` and `address_display: "Address shared in your invitation link"` — the real address is only revealed in the rendered Mehendi event view *if* the hydrated party is invited.

### 6.3 `data/guests.json` — full schema

This is the file the couple maintain. Generated with `tools/generate-codes.html`.

```jsonc
{
  "version": 1,
  "generated_at": "2026-10-01T00:00:00+02:00",
  "parties": [
    {
      // ---- Identity ----
      "invite_code":     "K7M2QH",       // 6 chars, Crockford base32, last char is mod-37 check
      "party_name":      "Naidoo family", // How we address them on the welcome banner
      "household":       "Naidoo",        // For grouping on admin (surname / household label)

      // ---- Members ----
      "guests": [                         // ≥1, each can RSVP individually for each event
        { "id": "g1", "first_name": "Priya",  "last_name": "Naidoo", "is_child": false },
        { "id": "g2", "first_name": "Devan",  "last_name": "Naidoo", "is_child": false },
        { "id": "g3", "first_name": "Anjali", "last_name": "Naidoo", "is_child": true,  "age": 8 }
      ],

      // ---- Invitation scope ----
      "events_invited": ["mehendi", "nalangu", "ceremony"],   // FK → events.json ids
      "plus_one_allowed": false,          // If true, RSVP form shows "+1 name" field
      "vip":              false,          // Used for admin sorting only

      // ---- Optional overrides ----
      "address_line":     null,           // Optional: postal address for thank-you cards later
      "phone":            "+27 82 555 0123", // For day-of WhatsApp blasts (kept off the wire)
      "notes_internal":   "Theo's first cousin"  // Private to the couple — never rendered
    }
  ]
}
```

**Field notes:**

- `invite_code` is uppercase Crockford base32, exactly 6 characters. The 6th character is a mod-37 check char (see §7). Codes are case-insensitive on lookup.
- `guests[]` is the source of truth for headcount. Each guest gets their own row in the RSVP form for dietary input.
- `events_invited` controls which event pages show the "You're invited" badge and which events the RSVP form lists.
- `plus_one_allowed` is rare and used sparingly (it complicates catering counts).
- `phone` and `notes_internal` are **never rendered to the page** — they're only useful when the couple is debugging or doing manual sends.

## 7. Invite code system

### Format

- **Alphabet:** Crockford base32 — `0123456789ABCDEFGHJKMNPQRSTVWXYZ` (no `I`, `L`, `O`, `U` to avoid visual confusion).
- **Length:** 6 characters.
- **Structure:** 5 random characters + 1 mod-37 check character.
- **Case:** Codes are stored uppercase. Lookups are case-insensitive (`toUpperCase().trim()`).

### Check character

Defined in `js/guests.js#checkCharFor`. Takes the first 5 chars, treats each as its Crockford base32 value (0–31), computes `sum = (sum * 32 + idx) mod 37`, and indexes into the 37-symbol alphabet `0123456789ABCDEFGHJKMNPQRSTVWXYZ*~$=U`. This catches single-character typos and most transpositions.

Note: in the prototype, validation is *soft* — invalid check chars are accepted if the code exists in `guests.json`. Production should enforce the check.

### URL format

```
https://shivanieandtheo.co.za/?i=K7M2QH
```

The code is read by `js/guests.js#getInviteCodeFromUrl` on bootstrap. The query parameter survives across hash route changes.

### Generation

Use `tools/generate-codes.html` in a browser. Paste the guest list (one party per row), get back the same list with a fresh, unique 6-char code per party. Codes are generated with `crypto.getRandomValues` (cryptographically random) so collisions across ~200 parties are astronomically unlikely.

### Privacy considerations

- Codes are **per-party, not per-guest** — guests within a party share a link.
- Codes are short and guessable in theory (32^5 ≈ 33M combinations, mod-37 check). This is fine for our threat model (a wedding, not a bank). Worst case: someone gets the wrong link and sees event details for a party they don't belong to.
- The bride's home address is only rendered when the URL's invite code resolves to a party invited to the Mehendi.
- `noindex, nofollow` on the site, plus `robots.txt` `Disallow: /`, keeps invite URLs out of search engines.
- `data/guests.json` should be **gitignored** in any public mirror. If hosting the source on a private GitHub repo (recommended), it can stay tracked.

## 8. RSVP flow (step-by-step UX)

1. Guest taps WhatsApp link → opens `https://shivanieandtheo.co.za/?i=K7M2QH`.
2. App bootstraps, reads `?i=`, fetches `data/guests.json`, finds party. Stashes party in state.
3. **Welcome banner** appears under the header: "Vanakkam, *Naidoo family* — Open your invitation ›"
4. Guest clicks RSVP (banner CTA, header CTA, or home CTA).
5. RSVP form shows:
   - Party name (read-only)
   - For each event in `events_invited`: a section with one row per guest, "Yes / No" toggle.
   - Per-guest dietary text input.
   - Message to couple (textarea, optional).
   - Song request (text input, optional).
6. As the user types, a **draft is auto-saved** to localStorage under `rsvp-draft:<code>` (so a closed tab doesn't lose work).
7. On Submit:
   - Client validates at least one guest is attending at least one event (or all "No" for a clear decline).
   - Payload is written to localStorage under `rsvp:<code>` (always).
   - If `BACKEND_URL` is set, payload is POSTed to the Apps Script endpoint.
   - On success → navigate to `#/thanks`.
   - On network failure → payload is queued in `rsvp-pending-syncs` and drained on next page load.
8. **Update flow:** revisiting `#/rsvp` with the same invite code pre-fills the form with the saved submission. The user can edit and re-submit.
9. **Bad code flow:** `?i=` resolves to no party → state stays public, no welcome banner, RSVP page shows a "We don't recognise this link" message and a `mailto:` to the couple.

## 9. Admin dashboard (`/admin/`)

A standalone HTML page (not part of the SPA). Passphrase-gated client-side (passphrase hashed and compared — not real security, just keeps casual guests out).

**Features:**

- **Totals tile row:** total parties, total invited guests, RSVPs received, RSVPs pending, total attending per event.
- **Parties × events grid:** rows = parties, columns = three events. Cells = "✓ 4/4", "✗ declined", or "—" (no response). Click row to see breakdown.
- **Per-event headcount with dietary roll-up:** filterable list for the caterer.
- **Exports:** download CSV (one row per guest per event) for the planner; download JSON of all submissions for backup.
- **Two data sources:**
  1. `localStorage` (whatever's in this browser — useful when running the prototype locally).
  2. `GET BACKEND_URL` (returns the Live tab as JSON when production is wired up).

## 11. Accessibility commitments

The site targets **WCAG 2.1 AA** and the following non-negotiables. See `ACCESSIBILITY.md` for the full audit checklist.

- Body text colour-contrast ≥ 4.5:1. Decorative gold on cream is *only used* for ornamental motifs and large display headings (≥ 24px bold = 3:1 allowance).
- All interactive elements ≥ 44×44 px tap target.
- Form inputs ≥ 16px font size (prevents iOS Safari auto-zoom).
- Full keyboard navigation: Tab order through header → main → footer; RSVP form fully keyboard-operable; Esc closes mobile nav.
- Visible focus rings on every focusable element (gold-dark outline, ≥ 2px).
- `skip-to-content` link is the first focusable element.
- `prefers-reduced-motion: reduce` honoured — countdown tick stops, transitions disabled.
- `aria-live="polite"` on the view container so route changes are announced.
- Semantic HTML: real `<header>`, `<main>`, `<nav>`, `<footer>`, `<article>`, headings in order.
- Tamil-script content marked with `lang="ta"` for screen-reader pronunciation hints.
- Mobile-first; usable at 320px viewport width.

**Lighthouse target:** Accessibility ≥ 95 on home, RSVP, and event detail pages.

## 13. Go-live checklist

Execute in order. Each step ends with a smoke-test action. *Time estimate: ~90 minutes for someone who has done it before; 2–3 hours first time.*

1. **Finalise content.** Replace all `[TODO: confirm with couple]` placeholders in `js/views/story.js`. Add real proposal photo to `assets/photos/`. Done when no TODO greps in `js/views/*`.
2. **Generate guest list.** Open `tools/generate-codes.html` in a browser, paste the full guest list (one party per line with members, events-invited, plus-one flag). Save the output as `data/guests.json`. Smoke-test: open `?i=<first-code>` and confirm the welcome banner shows the right party name.
3. **Register domain.** Cloudflare Registrar → `shivanieandtheo.co.za`. ~R200/year. (Alternative: Hetzner / domains.co.za — pick whichever has the better admin UX.)
4. **Create the GitHub repo.** Private. Push `06-Website/` contents to `main`. Confirm `data/guests.json` is **included** (private repo, fine) but the *legacy* Wedding folders aren't accidentally pushed.
5. **Create Google Sheet.** "Shivanie & Theo RSVPs". Three tabs: `Submissions`, `Parties`, `Live`. See `PRODUCTION.md` §2 for column layouts.
6. **Deploy the Apps Script.** Open the Sheet → Extensions → Apps Script → paste `Code.gs` from `PRODUCTION.md` §3 → Deploy → New deployment → "Web app" → Execute as **Me**, Access **Anyone**. Copy the deployment URL.
7. **Paste BACKEND_URL.** In `js/persist.js`, set `const BACKEND_URL = '<the URL>'`. Commit and push.
8. **Connect Cloudflare Pages.** Cloudflare dashboard → Workers & Pages → Create → Connect to Git → pick the repo. Framework preset: **None**. Build command: *(blank)*. Output directory: `06-Website`. Deploy.
9. **Connect custom domain.** Pages project → Custom domains → add `shivanieandtheo.co.za` and `www.shivanieandtheo.co.za`. Wait for DNS + cert (~5 minutes).
10. **Smoke-test 5 categories of guest links:**
    - (a) Party invited to **all 3 events** — should see 3 "You're invited" badges and 3 events on RSVP form.
    - (b) Party invited to **ceremony + nalangu only** — Mehendi should *not* show the badge or the bride's address.
    - (c) Party invited to **ceremony only** — only one event on RSVP form.
    - (d) Party with `plus_one_allowed: true` — RSVP form shows the +1 field.
    - (e) **Bad code** (`?i=ZZZZZZ`) — no welcome banner; RSVP page shows the "we don't recognise this link" message.
    - For each: submit a test RSVP and confirm a row appears in the Sheet's `Submissions` tab.
11. **Admin dashboard test.** Open `shivanieandtheo.co.za/admin/` → enter passphrase → confirm the test RSVPs from step 10 are visible. Export CSV.
12. **Delete the test submissions** from the Sheet (or move to a `Test` tab).
13. **Sleep on it.** Don't send anything yet. Re-open the site the next morning on a different device.
14. **Send Save the Dates** (`whatsapp-templates/01-save-the-date.md`) — *July 2026 latest*.
15. **Send Formal Invitations** with personalised links (`whatsapp-templates/02-formal-invitation.md`) — *10 October 2026*.

## 14. Open questions / known limitations

- **Withjoy export?** None — we're not migrating from anywhere.
- **What if Apps Script quota is exceeded?** Daily quotas for `UrlFetchApp` / `doPost` are 20,000+ per day on free accounts. We expect ~200 submissions. Non-issue.
- **What if a guest doesn't have WhatsApp?** Manual SMS or phone call by the couple. Their personalised link still works.
- **What if the bride's home address leaks?** Worst case is a stranger gets the address. Mitigation: don't publish on the open web; only render when the resolved party is invited to Mehendi.
- **Mobile data signal at Maroupi?** Variable. Final-logistics WhatsApp includes the venue maps link so guests can offline-cache directions.
